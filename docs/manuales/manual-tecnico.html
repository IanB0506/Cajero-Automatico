1. Descripción general

El sistema es un switch transaccional: recibe mensajes ISO 8583:1987 de terminales (cajeros y POS) por un socket TCP, los traduce a llamadas REST/JSON hacia un Core Bancario que mantiene cuentas y transacciones en SQL Server, y responde a la terminal con el mensaje ISO correspondiente y el código de acción en el DE 39. La misma aplicación sirve un cajero web y un panel de administración para la demostración.

Flujo de una transacción (retiro 0200)

  1. La terminal envía la trama precedida de su longitud. Spring Integration la recibe en un Virtual Thread.
  2. RecolectorTransaccionalService la parsea con j8583. Si es ilegible responde 30 sin cerrar la conexión.
  3. Si el par RRN + STAN ya fue respondido, devuelve la misma respuesta (retransmisión).
  4. Si faltan STAN, RRN o cuenta, responde 30.
  5. Arma un TransaccionCoreRequest (record) y lo envía a POST /api/core/transacciones con la cabecera X-API-Key.
  6. El Core bloquea la cuenta, valida estado, PIN, monto, límite y saldo, aplica el débito y registra la transacción en una sola transacción de BD.
  7. El Recolector arma la respuesta 0210 con DE 38, DE 39 y DE 54 y guarda en la caché las respuestas definitivas (no 68, 91 ni 96).

Concurrencia

  • Cada conexión TCP tiene su propio Virtual Thread; el código es bloqueante y secuencial (socket, HTTP, JDBC) sin agotar hilos del sistema operativo.
  • spring.threads.virtual.enabled=true aplica Virtual Threads a Tomcat y a las tareas programadas.
  • No se usa synchronized en caminos con E/S (se usa ReentrantLock), para no fijar el hilo virtual a su hilo portador.
  • Pool JDBC de 20 conexiones (Hikari) y pool HTTP de 500 conexiones keep-alive hacia el Core.

3. Protocolo ISO 8583

3.1 Enmarcado

  • Cada trama va precedida por 2 bytes con su longitud (entero sin signo, big-endian), sin contar esos 2 bytes. La respuesta usa el mismo enmarcado.
  • Tamaño máximo de trama: 8.192 bytes (recolector.tcp.max-frame-bytes).
  • La conexión puede quedar abierta para varias transacciones; se cierra tras 30 s sin actividad (recolector.tcp.timeout-ms).
  • Codificación ASCII, bitmaps en hexadecimal, cabecera opcional ISO015000050 (las respuestas la incluyen).

3.5 PIN block (DE 52)

PIN 1234, PAN 4532000000000001
bloque PIN = 0 | longitud | PIN | relleno F                -> 041234FFFFFFFFFF
bloque PAN = 0000 | 12 dígitos del PAN sin el verificador  -> 0000200000000000
DE 52      = bloque PIN XOR bloque PAN                     -> 041214FFFFFFFFFF

El Core recupera el PIN con el PAN de la cuenta y lo compara en tiempo constante con SHA-256("numeroCuenta:PIN"). El bloque viaja sin cifrar bajo una ZPK porque el sistema no incluye un HSM.

3.6 Saldos (DE 54)

Dos bloques de 20 caracteres: tipo de cuenta (10), tipo de monto (01 contable, 02 disponible), moneda, signo (C/D) y 12 dígitos en centavos. Ejemplo con Q1,400.00: 1001320C000000140000 + 1002320C000000140000.

4. Core Bancario y modelo de datos

El esquema lo crea init_sqlserver.sql (la aplicación no modifica el esquema: ddl-auto: none). El script es idempotente: crea lo que falta sin borrar datos, activa READ_COMMITTED_SNAPSHOT, crea índices y carga las cinco cuentas de demostración; si encuentra una columna pin en claro la convierte a pin_hash y la elimina.

CREATE TABLE dbo.cuentas (
    id BIGINT IDENTITY(1,1) NOT NULL PRIMARY KEY,
    numero_cuenta VARCHAR(30) NOT NULL,          -- índice único idx_cuenta_num
    pan VARCHAR(19) NOT NULL,                    -- índice idx_cuenta_pan
    titular VARCHAR(100) NOT NULL,
    saldo_disponible DECIMAL(15,2) NOT NULL,
    saldo_contable DECIMAL(15,2) NOT NULL,
    limite_diario DECIMAL(15,2) NOT NULL DEFAULT 500.00,
    retirado_hoy DECIMAL(15,2) NOT NULL DEFAULT 0.00,
    fecha_ultimo_retiro DATE NULL,
    estado VARCHAR(20) NOT NULL DEFAULT 'ACTIVE', -- ACTIVE, BLOCKED, EXPIRED
    pin_hash VARCHAR(64) NULL,                   -- SHA-256 de 'numero_cuenta:PIN' en hexadecimal
    intentos_pin_fallidos INT NOT NULL DEFAULT 0,
    banco VARCHAR(60) NULL
);

CREATE TABLE dbo.transacciones (
    id BIGINT IDENTITY(1,1) NOT NULL PRIMARY KEY,
    rrn VARCHAR(12) NOT NULL,                    -- UNIQUE (rrn, stan): uk_tx_rrn_stan
    stan VARCHAR(6) NOT NULL,
    numero_cuenta VARCHAR(30) NOT NULL,          -- índice idx_tx_cuenta
    cuenta_destino VARCHAR(30) NULL,
    monto DECIMAL(15,2) NOT NULL,
    tipo_operacion VARCHAR(20) NOT NULL,         -- COMPRA, RETIRO, CONSULTA, TRANSFERENCIA, DEVOLUCION, REVERSA
    saldo_anterior DECIMAL(15,2) NULL,
    saldo_posterior DECIMAL(15,2) NULL,
    codigo_respuesta VARCHAR(2) NOT NULL,        -- DE 39
    codigo_autorizacion VARCHAR(6) NULL,         -- DE 38
    terminal_id VARCHAR(30) NULL,
    fecha_hora DATETIME2 NOT NULL DEFAULT SYSDATETIME()
);

Reglas de negocio

  1. Bloqueo: la cuenta se lee con bloqueo pesimista (UPDLOCK, HOLDLOCK, ROWLOCK); en transferencias se bloquean ambas cuentas en orden de id para evitar interbloqueos.
  2. Validaciones, en orden: cuenta existente y, si viene el PAN, que corresponda a la cuenta (14) → estado bloqueado (05) o expirado (54) → PIN, obligatorio en retiro, consulta y transferencia y verificado siempre que venga (55; al tercer fallo 75 y la cuenta pasa a BLOCKED) → monto mayor que cero (13) → límite diario de retiro (61) → saldo (51).
  3. Aplicación: débito o crédito de los saldos disponible y contable, acumulado diario de retiros y registro de la transacción (también las rechazadas) en la misma transacción de BD.
  4. Idempotencia: si el par (RRN, STAN) ya existe, la inserción falla, todo se revierte y se devuelve la respuesta original.
  5. Reversa: busca la transacción original aprobada por RRN, acredita su monto (y descuenta el acumulado diario si era retiro) una sola vez; si no existe responde 25.
  6. Autorización: códigos secuenciales de 6 dígitos.
  7. Reset de demostración (POST /api/core/reset): borra las transacciones, reinicia acumulados e intentos de todas las cuentas y devuelve las cinco cuentas semilla a su saldo, límite, estado y PIN iniciales.

6. Seguridad

ElementoControl
Transacciones del CoreSolo el Recolector (cabecera X-API-Key, comparación en tiempo constante) o un administrador.
Administración y métricasRol ADMIN con HTTP Basic. Usuario y contraseña por variables de entorno; contraseña con BCrypt, calculada en el primer login.
Consultas y simuladorPúblicos (no exponen PIN ni hash).
PINHash SHA-256 en BD; PIN block en la trama; eliminado de respuestas y enmascarado en el simulador; 3 intentos fallidos bloquean la tarjeta.
SesiónAPI sin estado (sin cookies), por eso CSRF no aplica. La interfaz guarda las credenciales solo en memoria de la pestaña y cierra la sesión ante un 401.
Trama TCPTamaño máximo de 8 KB; tramas ilegibles responden 30 sin afectar la conexión.
ContenedorDistroless sin shell ni gestor de paquetes, usuario nonroot (65532), solo el binario.
Para producción faltaría: cifrar el PIN block bajo una ZPK y verificarlo en un HSM, TLS (o mTLS) en el socket TCP y en HTTP, y gestionar las credenciales con un almacén de secretos en lugar de .env.

9. Operación y monitoreo

Salud

GET /actuator/health
{"status":"UP","components":{"db":{"status":"UP"},"tcpIso":{"status":"UP"},"diskSpace":{...},"ping":{...},...}}

Con credenciales de administrador, tcpIso incluye el puerto y las conexiones abiertas. El contenedor usa el mismo endpoint en su HEALTHCHECK.

Métricas del switch

GET /api/iso/metricas
{"transaccionesProcesadas":5,"transaccionesAprobadas":4,"transaccionesRechazadas":1,"tramasConErrorFormato":0,
 "tcpPuerto":15000,"tcpEstado":"ACTIVO (Listening)","tcpConexionesAbiertas":0,
 "modoConcurrencia":"Virtual Threads (Project Loom)","recolectorBasura":"ZGC ...","memoriaRssMb":964,...}

/actuator/metrics (ADMIN) expone las métricas de Micrometer; en modo JVM, jvm.gc.pause muestra las pausas de ZGC. El binario nativo usa Serial GC y no publica esa métrica.

Registros

  • Arranque: Started RecolectorApplication in X seconds y un resumen con los puertos.
  • Advertencias de negocio: tramas ilegibles, MTI no soportados, bloqueo de tarjeta por intentos de PIN, Core no disponible.
  • Nivel por paquete: logging.level.com.banco.recolector (por defecto INFO; DEBUG muestra cada trama sin datos sensibles).

Datos de demostración

POST /api/core/reset (o Restaurar datos en el panel) devuelve las cuentas semilla a su estado inicial. docker compose down -v borra la base completa; el siguiente up la recrea.

11. Solución de problemas

SíntomaCausaAcción
cajero-app no pasa a healthyLa BD no está lista o las credenciales no coinciden.docker compose logs app; revisar MSSQL_SA_PASSWORD; si se cambió después de crear el volumen, docker compose down -v.
cajero-db-init termina con errorSQL Server no aceptó la conexión o el script falló.docker compose logs db-init.
La compilación nativa se interrumpeMemoria insuficiente en Docker.Asignar 8 GB o más a WSL 2, o usar APP_DOCKERFILE=Dockerfile.jvm.
"Port is already allocated"Puerto ocupado en el equipo.Cambiar APP_HTTP_PORT, APP_TCP_PORT o SQLSERVER_PORT en .env.
Todas las transacciones responden 91El Recolector no alcanza al Core.Revisar recolector.corebancario.url y que la app escuche en ese puerto.
Todas las transacciones responden 96La API Key del Recolector no coincide con la del Core (el Core responde 401).Usar el mismo CORE_API_KEY.
El binario nativo no conecta a SQL Server (codepage Cp1252)Imagen compilada sin todos los charsets.Compilar con el perfil native del pom.xml (incluye -H:+AddAllCharsets).
Los scripts de JMeter fallan con "Unsupported class file major version 69"JMeter 5.6.3 ejecutado con Java 25.Usar el servicio jmeter de Compose o Java 17/21 para JMeter.
401 en operaciones de administraciónCredenciales distintas a ADMIN_USER/ADMIN_PASSWORD.Revisar .env y reiniciar la app.
